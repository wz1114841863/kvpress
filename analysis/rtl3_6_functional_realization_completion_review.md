The following bounded no-model evidence is valid and remains required:

1. RTL3.1 supplies a host-side functional memory environment only through
   accepted `core_mem_if_v1` transactions; it is not an HBM controller.
2. RTL3.2 joins the four exact packed-read grants and proves typed functional

   non-inferred testbench boundary.
3. RTL3.4-B supplies a pure-software R4 oracle that consumes only accepted
   packet bytes and accepted R6 work; it is not Chisel numeric RTL.
4. RTL3.5-B supplies the sole functional partial producer from frozen
   query/source facts, and RTL3.5-C proves one exact packet's byte/identity
   acceptance in the existing Chisel source-packet/R4 structural path.
5. RTL2.6.5c/5e historically record accepted-carrier success, fault, stale,
   and bounded ready-low replay plus a same-instance R3-to-reclaim witness,
   but that witness still contains explicit S2 fill and R4 result verification
   endpoints. RTL3.6's attempted replay preflight also found that the active
   terminal and reclaim scoreboard bindings have stale hash-bound sources, so
   this historical replay record is not revalidated evidence at this review.

## Result: no functional-realization PASS yet

The planned logical sequence remains the target:

```text
RETAIN -> pending -> functional memory -> P3 -> publication
-> functional packed read -> S2 -> functional partial provider
-> functional R4 merge -> terminal -> retire -> reclaim
```

It is **not** yet one live same-instance functional composition.  The review
therefore freezes these four residual gaps:

1. No same-instance live binding carries a functional partial provider packet
   through R4 to the matching R6 terminal; RTL3.5-C is intentionally a static
   fixture, not a live bridge.
2. No same-instance binding carries a functional R4 terminal through R6
   retirement and same-R5 durable reclaim; RTL2.6.5e still drives an R4 result
   stub.
3. S2 sidecar transport remains the explicit RTL3.2 testbench ingress and is
   not generated by the functional memory environment or a named sidecar
   owner.
4. Existing reset/stale checks are bounded component/protocol evidence; no
   full-path reset-epoch composition witness binds all of the above owners.
5. The active RTL2.4.3 terminal and RTL2.5.5 reclaim replay bindings contain
   source-hash drift against their current Chisel/doc dependencies. Their
   event replay must not be counted as newly passing RTL3.6 evidence until a
   narrow provenance repair re-audits those bindings.

Consequently, this review does not authorize a production top, live
Python/Chisel co-simulation, Chisel attention MAC/RoPE/FP implementation,
HBM/SRAM/controller realization, profiling, timing/throughput/area/energy/PPA,
model/GPU execution, or a new A4 DSE.
